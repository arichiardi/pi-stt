# Plan - voice as the pi session channel

Reference decisions: `docs/adr/0001-sessao-pi-unica-cabeca.md` and `glossary.md`. This plan does not implement anything yet.

## Technical boundary

- **Input:** consolidated transcription → user message in the pi session (`steer` when a run is in progress).
- **Output:** text produced by pi → synthesis → playback. Voice never generates content.
- Realtime gets no permission to answer on its own: the voice session only transcribes, and synthesis receives only text from pi.

## Playback states (new)

Each synthesized utterance has a record in one of these states:

| State | Meaning |
|---|---|
| `pending` | text received, audio has not started |
| `playing` | audio in progress |
| `done (estimated)` | the timer shows the audio finished without interruption. It does not mean the user heard it |
| `interrupted` | the user spoke, or `/stt-live stop` cut the audio; record the estimated heard fraction |

Rule: `done` means playback finished, not proven understanding or listening. Until a reliable player event exists, the timer records estimated completion. pi may only assume that an explanation was *played* in state `done (estimated)`, never that it was heard. Meaning of `done (estimated)`: the audio is estimated to have finished playing; that finish is not observed. In `interrupted`, pi receives this in the history as "answer interrupted at ~X%", and can present the rest again as text or voice.

Technical limit: the `Player` gets no confirmation of how much was heard. Today the end is inferred by a timer (`index.ts:105`). The `interrupted` fraction will be estimated from the PCM sent and the elapsed time, and must be marked as an estimate.

## History: equivalent, not identical

Criterion: voice and typing preserve **content, order, and references**. They may differ in punctuation, capitalization, and source metadata (`source: voice`, timestamps). Byte-for-byte equality is not required.

## Implementation order

1. **Acceptance tests** (before any production code).
2. **Playback states and interruption record**, with simulated synthesis.
3. **Transcription as input only** (no answer generation by realtime).
4. **Synthesis** from pi text. Kokoro local first; API TTS only if the Kokoro proof fails.
5. **Spoken summary** generated by pi in the same run as the visual answer.

## Acceptance tests

**T1 - History equivalence.** Same conversation sequence by voice and by typing ("explain X", then "fix that"). Check that the pi history has the same content, order, and references; that the second message resolves the reference; and that the source (voice/text) is marked.

**T2 - Steer during a run.** pi is in a long run. Starting to speak must:
- stop the audio in playback;
- send the consolidated transcription as `steer`;
- **not** cancel the run;
- record the previous answer as `interrupted`.

This test protects the most delicate distinction in the design.

**T3 - Playback state.** Short answer spoken to the end → `done (estimated)` (the test does not prove listening). Same answer interrupted in the middle → `interrupted` with a fraction > 0 and < 100%. Check the text received by the simulated synthesis and the playback events.

**T4 - No conversational autonomy.** Input that is not a request ("hi", "how are you?") produces only a transcription and passes through pi; synthesis speaks only text given by pi. No audio output starts in realtime.

**T5 - Decision boundary.** pi asks for approval: voice announces it; a spoken "yes" authorizes nothing (no approval is sent).

## Kokoro criterion (proof before adoption)

The proof uses the existing script (`~/.pi/agent/voz/kokoro_speak.py`), not inspected in detail yet beyond reading the code:

- **Quality in pt-BR:** a sample you evaluate, with phrases from real use.
- **Time until it starts speaking:** measured from the call, with the model loaded and cold. The current script reloads the model on every invocation, which tends to be the bottleneck. If the number is high, the alternative is a persistent process.
- **Interruption:** initial target of 20 ms, with the measurement made explicit. Two separate intervals: (a) from speech detection to the `Player.stop()` call; (b) from detection to sound actually stopping, measured by output capture. Interval (a) does not prove that the sound stopped, because driver buffers can keep playing after the process is killed. Only (b) proves the target.

Measure cold start (first call, with model loading) and calls with the model already loaded separately. A persistent process is only justified if loading dominates the latency **and** quality is good enough; the memory cost also needs validation.

Not every failure points to switching TTS, because each problem has a different origin:
- **Quality in Portuguese:** the synthesizer (model, g2p phonemes).
- **Delay:** loading (cold start) or per-chunk processing.
- **Slow interruption, or audio that keeps playing:** the player (buffers, killing the process).

Switching to an API can keep the playback problem, which does not depend on the synthesizer. Diagnose the origin before switching.
